# v4.0 学习与答辩指南

用户有 C++ 基础，Java 从项目开始学习。先解释业务与真实调用，再解释语法，不要求从零默写整套代码。

## 第一课：一条商品查询

在 IDEA 打开 `controller/CatalogController.java` 的 find，然后依次打开 `service/CatalogService.java`、`mapper/ProductMapper.java`、`src/main/resources/mapper/ProductMapper.xml`、`model/Product.java`。

请求示例：`GET /api/products?scope=market&category=生活用品&q=台灯`。身份由 SessionFilter 验证服务器会话后写入 request attribute，不能靠客户端传用户编号冒充。

Controller 提取参数→Service检查用户及scope→通过MarketRepository提供的类型化Mapper调用ProductMapper.search→MyBatis寻找namespace和id对应的XML→绑定参数执行MySQL查询→resultMap把每行转换为Product→Service转成ProductResponse→Controller返回JSON。

页面首页仍先用 `/api/market` 取得组合数据，再在浏览器筛选；`/api/products` 是可独立调用、已测试的服务器动态查询接口。不要把两条路径混为一谈。

## 第二课：读懂 Mapper XML

```xml
<mapper namespace="com.example.demo.mapper.ProductMapper">
  <select id="findById" resultMap="row">
    SELECT <include refid="columns"/>
    FROM products WHERE product_id=#{id}
  </select>
</mapper>
```

namespace 对应接口全名，id 对应接口方法名。row 是同文件声明的 resultMap，不是 Java 类别名。resultMap 的 type 写 Product 全限定名，里面显式列出 column/property。

`#{id}` 是预编译参数绑定，不是字符串直接拼 SQL。多参数方法使用 @Param；XML 的动态 where/if/choose 根据分类、关键词、scope 生成 SQL。关键词采用字面包含，不把 `%` 当作任意字符。

自测：XML的id写成findByID而接口是findById会怎样？运行时找不到对应的映射语句，方法名大小写必须一致。

## 第三课：发布与主键

POST products→CatalogService.save：验证字段→Product.builder创建商品→ProductRepository.save委托ProductMapper.insert→MySQL生成product_id并回填→插入图片→提交事务→返回201。

当前Builder先设置seller_id，build返回独立对象，然后Service填写验证过的业务字段。对象生成与SQL主键生成是两件事。若图片写入异常，商品插入也回滚；自增编号允许出现间隙。

ProductRepository保留findAll/findById/findByCategory/save/update/deleteById六方法，便于衔接前一阶段练习。其工作副本重载已经删除。

## 第四课：Java 与 Spring

| C++已有经验 | 当前Java对应 |
|---|---|
| 类、构造函数 | class、new、同名构造方法 |
| 引用/指针 | 对象变量保存引用，Java无手动delete |
| vector | List/ArrayList与泛型 |
| 接口/抽象类 | Mapper是interface，MarketSupport是abstract class |
| const成员 | final引用不能重新赋值，不代表引用对象不可变 |
| 数据结构 | 请求/响应DTO采用record，访问器是input.title() |
| 异常 | BusinessException触发事务回滚并映射HTTP状态 |

Spring扫描Controller/Service/Repository并通过构造方法装配对象；@MapperScan为接口创建MyBatis代理，因此不需要自己编写ProductMapperImpl。@Transactional由Spring代理管理事务，不能把它理解成普通注释；同类内部调用不会自动经过另一个方法的事务代理。

v3使用Operation匿名回调配合全量工作副本，v4已改为声明式事务。Java应用集合处理仍用普通循环；switch的case箭头不是Lambda。

模型保留public字段，XML显式映射字段；DTO是对外边界，不直接返回含凭据的模型。User/Admin中的密码字段带@JsonIgnore。

## 第五课：下单不是一条INSERT

1. 校验用户和商品编号。
2. `SELECT ... FOR UPDATE` 锁商品行，检查可售状态和禁止自买。
3. 从服务器商品价格、个人地址生成订单快照。
4. 插入订单，将商品改为锁定。
5. 同一个Service事务提交；失败全部回滚。

另一个买家购买同一商品时等待该行锁，锁释放后读到最新状态。数据库有效订单唯一索引进一步约束重复订单。@Transactional本身不代替业务校验或行锁。

快递发货/收货与退款以订单行为共同锁点。金额用整数分，快递演示运费600分，自提0分；订单的历史成交价与运费不会因商品或地址后来修改而变化。

## 第六课：数据库材料为什么不直接导入

上传报告正文是十二表，旧SQL是SQLite十三表。condition_label、rating、real_name、conversation_products属于旧版；MySQL不支持直接执行PRAGMA。新schema与insert-demo是核对后的MySQL实现，差异见报告核对文档。

会话initiator_id在v4记录实际发起者。pair_low/pair_high是仅供唯一约束的技术生成列；并非重新添加“会话商品表”。

## 答辩演示顺序

1. 展示MySQL十二表、外键、订单联表查询。
2. 指出ProductMapper接口、XML、实体三个文件如何对应。
3. 用户注册并发布，管理员审核，另一用户下单和模拟付款。
4. 卖家发货、买家收货和文字评价；演示聊天、退款或举报。
5. 删除无历史商品返回204；有历史商品返回409；不存在详情返回空404。
6. 演示并发/回滚测试，再重启Java后展示数据保留。

使用不同浏览器会话区分买家、卖家、管理员。同一浏览器的多个标签共享Cookie，退出会影响同站点其他标签。

支付、物流、退款到账仍是模拟；当前没有生产级部署、找回密码或WebSocket。页面组合接口会读取全量数据，属于课程小规模方案，后续可在需求明确时增加分页。
