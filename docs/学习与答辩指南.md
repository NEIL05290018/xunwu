# 从 C++ 到本项目：学习与答辩路线

## 先说明你做的系统

“循物是一个校园二手交易课程平台。一个用户既能买也能卖。浏览器发 HTTP 请求，Java Spring Boot 校验业务规则，再通过 JDBC 访问 MySQL。管理员负责商品审核与举报处理。支付、物流和退款到账是模拟状态。”

不要把模拟付款说成支付接口；不要把 JSON 初始数据说成数据库。现在真实持久化是 MySQL 十二表。

## 先读一条查询

打开 `controller/CatalogController.java` 的 find → `service/CatalogService.java` 的 find → `repository/ProductRepository.java` → `repository/MarketRepository.java`。

- Controller 负责接收 category、q、scope 和**服务器写入的 userId 属性**，返回 HTTP 200；不在此创建商品列表。
- Service 判断这个用户能看到哪些商品，以及分类/关键词是否匹配。
- ProductRepository 提供商品数据方法；MarketRepository 执行 SQL。
- DTO `ProductResponse` 规定返回 JSON 的字段，前端 store.js 用 fetch 接收，app.js 生成卡片。

**自测：别人能否通过 `scope=all` 看到我的待审核草稿？** 不能，all 仍受身份可见范围限制。

## 再读发布商品

`app.js publish-form` → `store.js publish` → POST `/api/products` → `CatalogService.save`：

1. 校验价格、标题、分类、图片、交付方式。
2. 从当前服务器会话决定 seller_id，不接受客户端伪造卖家。
3. `Product.builder().seller_id(uid).build()` 创建独立对象；后续填写已验证字段。
4. ProductRepository 分配编号、保存工作副本及图片。
5. MarketRepository 在事务内写 products 和 product_images；返回 201。
6. 管理员通过审核后，商品才出现在公开在售列表。

**Builder 为什么每次 build 返回新 Product？** 如果直接返回同一个内部对象，后续修改 builder 或另一份商品会相互影响。

## C++ 与 Java 对照

| 已熟悉的 C++ 概念 | 本项目 Java 对应 |
|---|---|
| 类、对象、构造函数 | class、new、与类同名的构造方法 |
| 指针/引用 | 对象变量保存引用；没有手动 delete，用垃圾回收 |
| std::vector | List / ArrayList；泛型写 `List<Product>` |
| const 成员引用 | final 字段不能重新赋值，但引用对象不一定不可变 |
| 抽象基类/虚函数 | interface 或 abstract class；Operation 是接口 |
| 回调对象 | `new Operation<T>() { public T apply(...) {...} }` 匿名内部类 |
| 数据结构 | record DTO；访问器是 `input.title()`，不是 getTitle |
| 异常 | throw / try / catch；抛异常使当前数据库事务回滚 |

本版应用集合处理使用 for 循环。switch 中的 `case ... ->` 是 Java switch 语法，不是 Lambda；测试辅助代码允许使用 Lambda。

## Spring 对象由谁创建

`@SpringBootApplication` 从主类所在包开始扫描。`@RestController`、`@Service`、`@Repository` 注册 Spring Bean。Controller 构造方法需要 CatalogService，Spring 将它注入；Service 再需要 Repository。只有一个构造方法时不必写 `@Autowired`。

IoC 是对象创建/管理交给容器；DI 是通过构造方法提供依赖。前端 import 是 JavaScript 模块导入，不能把它称为 Spring DI。

## 登录之后为什么不能改请求头冒充别人

`AuthController` 校验密码哈希成功后，把 principalId、role 放到服务器 HttpSession，浏览器收到 HttpOnly Cookie。`SessionFilter` 读取会话，将 userId/adminId 放入当前请求属性。普通用户手写 X-Demo-Admin 不会成为管理员。

CSRF token 是页面通过 `/api/auth/session` 获取的随机值；写请求必须带 `X-CSRF-Token`。它与密码、用户编号不同。

## 为什么下单需要事务

两个买家同时点击一件商品，如果先查“在售”再各自写入，可能出现两个订单。本版先获取 MySQL 行锁，再读取数据、检查商品状态、创建订单、把商品改成锁定；整个过程提交或回滚。数据库还用唯一索引兜底。

**自测：运单号为空却先修改了 carrier，是否会保存半成品？** 不会，业务异常使事务回滚。**地址修改后为什么订单不变？** 订单里存的是下单时复制的快照。

## 建议答辩演示（约 8—10 分钟）

1. 展示十二表、外键和一个联表查询。
2. 注册普通用户，登录后发布商品。
3. 用另一浏览器会话登录管理员，通过审核。
4. 买家收藏、联系卖家、下单、模拟付款；卖家发货，买家收货、文字评价。
5. 展示退款或举报处理；尝试删除有订单历史的商品，说明 409。
6. 新建无历史商品并删除；再次查询返回空 404。
7. 重启 Java 应用后重新登录，展示业务数据保留。
8. 展示测试报告，说明已有验证和仍未实现的真实支付等边界。

准备普通用户、管理员两个浏览器窗口（可用无痕窗口）。同一浏览器同一站点共享会话，在多个标签页切换账号会互相影响。
